# 콜라브레인 퍼스널(CollaBrain Personal) 제품 기획서

---

# PART 1. 제품 정의

## 1.1 비전

> **일하는 사람이 자기 자신을 이해할 수 있는 세상.**

성과는 측정되지만, 그 성과를 만드는 "일하는 방식"은 아무도 보여주지 않는다. 우리는 개인이 남의 평가가 아닌 자기 데이터로 스스로를 이해하고, 스스로 발전할 수 있게 한다.

장기 제품 계보:
```
B2B      Understand your organization.
Personal Understand how you work.        ← 지금 만드는 것
Future   Work better with others.
```

## 1.2 목적 (Mission)

Collabrain observes your everyday work patterns, **shows you where you stand — against your own past and against others — and helps you understand what to improve next.**

- **진단하고, 관찰하고, 해석을 돕는다.** 본인이 자발적으로 요청한 진단은 감시가 아니다.
- **점수와 패턴을 함께 보여준다.** 점수는 한눈에 파악하는 용도, 패턴 서술은 그 점수의 맥락과 근거를 설명하는 용도. 점수만 있으면 성적표가 되고, 서술만 있으면 밋밋해진다 — 둘 다 필요하다.
- **과거의 나 + 익명화된 동료군, 둘 다와 비교한다.** 단, "동료와의 비교"는 **실명 개인이 아닌 익명 집단 평균**을 기준으로 한다 (아래 4장 안전장치 참고). 실명 비교는 관계(Connections) 모듈에서 여전히 금지된다 — 이건 다른 종류의 비교다.

### 실명 vs 익명 판단 기준

이 제품 전반에서 실명을 쓸지 익명 집단으로 처리할지는 **"이 정보가 정확히 누구 것인지 알아야 니즈가 충족되는가"**로 결정한다.

- 니즈가 특정 개인을 식별해야 충족되면 → 실명 (예: ⑥ 동료 사용설명서 — "이 사람과 일하는 법"은 누구인지 알아야 쓸모 있음)
- 니즈가 익명 상태로도 충족되면 → 익명 집단 처리 (예: 동료 벤치마크 비교 — "평소의 나보다 나은가"가 핵심이지 "정확히 누구보다 나은가"가 아님)

**소규모 팀 안전장치**: 벤치마크처럼 "익명이어도 니즈가 충족되는" 항목은, 비교 모수가 적어 사실상 익명이 깨지는 상황(예: 팀원 3명)에서는 **아예 표시하지 않는다.** 니즈 충족에 실명이 필요 없는 항목이므로, 안 보여줘도 잃는 게 없고 리스크만 없앨 수 있다. 최소 모수 기준(예: 10명 미만이면 비표시, B2B 익명 집계 풀과 혼합해 모수 보강)을 적용한다.

### 톤 원칙
"기분 나쁘지 않게, 그러나 객관적으로." 점수·순위를 있는 그대로 보여주되:
- 서열화된 언어 금지: "하위 20%" (X) → "평균보다 낮은 편입니다" (O)
- 모든 점수 옆에는 반드시 "그래서 무엇을 해볼 수 있는지" 행동 제안이 동반된다. 진단으로 끝나면 성격검사이고, 행동으로 이어지면 성장 도구다.

## 1.3 목표 사용자

### 1차 타겟 — "역할이 흐려진 중간 연차 실무자"
- **누구**: 3~10년차, Slack 기반으로 일하는 지식노동자 (기획·개발·디자인·PM)
- **특징**: 직함과 실제 하는 일이 벌어지기 시작한 시점. 실무자인데 조율이 늘고, 리드는 아닌데 책임은 늘어난 상태
- **왜 이들인가**: "나 요즘 무슨 일 하고 있지?"라는 질문이 실제로 발생하는 유일한 구간. 신입은 시킨 일을 하고, 리더는 이미 역할이 명확하다

### 2차 타겟 — "리모트/비동기 환경의 개인"
- Slack이 업무의 전부인 사람들. 데이터 커버리지가 가장 높고, 스스로를 관찰할 거울이 가장 부족함

### 3차 타겟 — "다른 사람을 이끄는 실무자" (⑨ 감사·인정 수지 코치 대상)
- **누구**: 팀 리드·PM 등 공식/비공식으로 다른 사람의 업무를 조율하거나 위임하는 역할을 겸하는 사람
- **1차 타겟과의 관계**: 겹칠 수 있음(3~10년차 실무자가 동시에 팀 리드인 경우 흔함) — 별도 유형이 아니라 **온보딩에서 "다른 사람을 이끄는 역할인가요?"로 식별하는 서브 세그먼트**
- **왜 1차가 아니라 3차인가**: 관리자·리더도 자기 자신을 돌아보고 발전하려는 니즈는 분명히 있고, 리더가 잘하면 팀 전체 분위기에 영향을 준다는 것도 맞다. 다만 PART 2의 니즈 우선순위 분석 기준으로 보면 "역할이 흐려진 실무자"(1차 타겟)가 겪는 페인(P1: 직함과 실제 업무의 괴리)이 더 첨예하고 보편적이라 후킹 니즈로서 강도가 높다. **니즈가 가장 강한 사용자를 1차로 두고, 리더 세그먼트는 그 위에 얹는 순서**로 간다
- **왜 필요한가**: ⑨(도움-인정 수지, 위임 비율 추적)는 팀을 이끄는 사람에게만 의미 있는 지표라 전체 사용자에게 노출하면 관련 없는 기능이 됨 → 온보딩 응답에 따라 선택적으로 활성화

### 명시적 비타겟
- **팀원을 관리·평가할 목적으로 쓰려는 관리자** (그건 B2B 제품). 3차 타겟은 "본인의 리더십 행동을 스스로 돌아보는" 용도이지 팀원을 평가하는 도구가 아님 — 이 경계는 ⑨ 설계에서도 유지
- 성격유형·적성 진단을 원하는 사람 (그건 우리 제품이 아님)

## 1.4 사용자 페인포인트

| # | 페인포인트 | 사용자의 실제 말 | 왜 지금까지 해결 안 됐나 |
|---|---|---|---|
| P1 | 직함과 실제 업무의 괴리를 본인만 모른다 | "나 요즘 뭘 하고 있는 건지 모르겠어" | 자기 업무를 객관적으로 집계해주는 도구가 없음. 캘린더 기반(Viva류)은 *시간*만 보고 *무슨 일인지*는 못 봄 |
| P2 | 과부하를 본인이 가장 늦게 안다 | "번아웃 오고 나서야 알았다" | 시간외 근무 인지는 되지만, "평소의 나 대비" 기준선이 없어 판단 불가 |
| P3 | 커뮤니케이션 습관은 지적받기 전엔 모른다 | "그런 식으로 말한다는 걸 몰랐다" | 피드백은 드물고 늦고 감정적임. 중립적 관찰자가 없음 |
| P4 | 조직 내 자기 위치를 볼 방법이 없다 | "내가 여기서 무슨 역할이지?" | 조직도는 공식 역할만 보여줌. 실제 협업 구조는 비가시 |
| P5 | 문제를 알아도 뭘 바꿔야 할지 모른다 | "고쳐야 하는 건 아는데 어떻게?" | 분석형 도구는 진단에서 멈춤. 행동 제안까지 안 감 |

## 1.5 솔루션 아이디어

Slack 협업 데이터를 AI가 지속 관찰하여, **주 1회 "이번 주 나에게 무슨 일이 일어나고 있는가"를 한 문장으로 알려주고, 그에 따른 작은 실험 하나를 제안**한다.

| 페인 | 솔루션 | 핵심 매커니즘 |
|---|---|---|
| P1 | 업무 구성 분해 + 자기인식 갭 | 메시지 *내용*을 업무 유형으로 분류 → 본인 인식과 대조 |
| P2 | 에너지 리듬 관찰 | 절대값이 아닌 "나의 4주 baseline 대비" 변화 감지 |
| P3 | 대화 습관 패턴 서술 | 점수 아닌 문장 + 관찰 지속 주수로 신뢰도 표시 |
| P4 | 관계 역할 서술 | 인사이트 먼저("You're becoming a bridge"), 그래프는 증거 |
| P5 | 이번 주 실험 1개 | 관찰 → 제안 → 다음 주 회고의 루프 |

**차별화 근거**: Viva Insights류는 시간·메타데이터(회의 몇 시간, 메일 몇 통)만 본다. 성격검사류는 자기신고 데이터만 본다. 콜라브레인은 **메시지 내용과 관계 그래프**를 본다 — 이 조합을 가진 제품이 없다. 게다가 MBTI·성격검사류와 달리, **실제 행동 데이터에서 나온 유형**이라 "그래서 이번 주 뭘 해볼까"까지 이어진다 — 자기신고 기반 유형 검사는 여기서 끝나지만 콜라브레인은 여기서 시작한다.

### 1.6 유형 + 점수 + 비교

B2B에 이미 있던 **히어로 맵**(부하×점수 2축, "스마트 워커/히어로/하드 워커/협업 단절" 4분면)을 그대로 개인용 **종합 유형(Work Type)**으로 재활용한다. 이건 신규 개발이 아니라 기존 자산 부활이다.

- **종합 유형**: 4분면 중 현재 위치 → "당신은 지금 하드 워커 유형입니다" 같은 한 줄 정체성. MBTI처럼 기억하기 쉬운 라벨을 부여하되, 자기신고가 아니라 실데이터 기반
- **6축 점수**: 기존 COMM-1~6 1레벨 지표를 0~100 점수로 그대로 노출 (레이더 차트). 점수 옆에 패턴 서술 병기
- **비교 기준 2종**: ① 과거의 나 (4주 baseline 추이) ② 익명화된 동료군 평균 (아래 4장 벤치마크 소스 참고)
- **행동 제안**: 가장 낮은 축 또는 가장 크게 변한 축을 골라 "이번 주 실험"으로 연결 (PART 3 실험 루프와 동일 메커니즘)

# PART 2. 니즈 정합성 재검토

설계를 페인포인트 기준으로 역검증한 결과.

## 2.1 검증 결과: 정합함

| 페인 | 설계 대응 | 판정 |
|---|---|---|
| P1 | 관점 B(업무 구성) + 자기인식 갭 | O — Phase 1 배치 적절 |
| P2 | 관점 C(에너지), baseline 대비 | O |
| P3 | 관점 D(대화 습관) | O — 단 Phase 2 배치는 포지셔닝상 타당 |
| P4 | 관점 A(관계) | O — 인사이트 우선 방식으로 적절 |
| P5 | 이번 주 실험 루프 | O — 제품의 리텐션 엔진 |

## 2.2 재검토에서 발견한 보완점

### 보완 1. Phase 1이 P1을 충분히 해결하는가 — coarse 분류의 한계
Phase 1의 업무 분류를 "Creating vs Coordinating" 2분류로 축소했다. 개발 리스크 관점에선 옳지만, **P1("나 요즘 뭘 하는지 모르겠다")의 해소력이 약해진다.** 2분류로는 "조율이 늘었다"까지만 말할 수 있고, "그래서 내 역할이 변하고 있다"는 서사가 안 나온다.

→ **조정**: Phase 1 분류를 **3분류(Creating / Coordinating / Resolving)**로 상향. 4분류(Planning 분리)는 Phase 2. Planning은 다른 셋과 경계가 가장 모호해서 분류기 난이도가 높으므로 뒤로 미루는 게 합리적이다.

### 보완 2. 첫 주에 가치가 0인 문제
콜드스타트 UX(Week1 "알아가는 중")는 정직하지만, **가입 첫 주에 볼 게 없으면 이탈한다.** 신뢰를 지키려다 리텐션을 잃는 구조.

→ **신규**: 온보딩 시 **과거 데이터 소급 분석**을 수행한다. Slack은 과거 메시지 히스토리를 제공하므로, 연동 즉시 지난 4~8주를 분석해 첫 인사이트를 바로 제공할 수 있다. "지난 8주를 살펴봤어요" 로 시작하면 콜드스타트 문제가 대부분 사라진다. Week1/2/4+ 메시지는 소급 데이터가 부족한 경우(신규 워크스페이스 등)의 fallback으로 유지.

> **원칙**: 소급 분석을 우선한다. **관찰 지속 주수는 항상 표기**한다 — 소급 분석 결과에도 "지난 8주 관찰 기준"을 함께 표시해 성급한 단정으로 읽히지 않게 한다.

> **향후 방향**: 소급 분석을 우선하는 건 지금이 붙여넣기 방식이라 과거 데이터를 매번 수동으로 가져와야 하는 제약 때문이다. **Slack API 연동이 되면 이 제약이 사라지므로, 그때는 Week1(알아가는 중) → Week2 → Week4+(패턴 확정)처럼 신뢰를 점진적으로 쌓아가는 방식으로 전환을 검토한다.** 실시간으로 데이터가 자연스럽게 쌓이는 구조에서는 "처음부터 8주치를 몰아서 보여주는 것"보다 "매주 조금씩 더 확실해지는 경험" 쪽이 신뢰 형성에 더 유리할 수 있다.

### 보완 3. P5 해결의 전제 — 실험 결과를 측정할 수 있는가
"다음 주 회고"를 하려면 실험 효과를 데이터로 측정해야 한다. 그런데 "위임해보세요" 같은 실험은 효과가 다음 주 데이터에 잡히지 않을 수도 있다.

→ **원칙 추가**: 실험은 **데이터로 관측 가능한 행동**으로만 제안한다. 관측 불가능한 실험(마음가짐, 태도)은 제안하지 않는다. 측정이 안 되면 회고가 공허해지고 루프가 끊긴다.

**단, 이 원칙은 "관찰만 하기" 옵션과 충돌하지 않는다.** 두 트랙은 측정 대상 자체가 다르다.

| 트랙 | 사용자 선택 | 다음 주에 보여주는 것 |
|---|---|---|
| 실험 트랙 | `[ I'll try this ]` | 제안한 행동의 변화 측정 — "조율 메시지가 15% 줄었습니다" |
| 관찰 트랙 | `[ Just observe this week ]` | 변화 측정 없이 baseline 재확인 — "이번 주는 평소 패턴이 유지됐습니다" |

관찰 트랙은 회고가 아니라 **baseline 갱신**이 목적이다. 모든 데이터 변화가 문제는 아니며, 사용자가 "지금은 바꿀 때가 아니다"라고 판단할 권리를 제품이 존중한다.

### 보완 4. 비타겟 방어 — "이거 관리자한테 보이나요?"
페인포인트 전체가 "남에게 평가받는 것"에 대한 불안과 인접해 있다. 온보딩 첫 화면에서 **"이 데이터는 당신만 봅니다. 회사·관리자는 접근할 수 없습니다"**를 명시적으로 선언해야 한다. 이건 부가 기능이 아니라 제품 신뢰의 전제 조건.

**주의**: 이 원칙은 "동료 비교"를 넣기로 한 결정과 공존해야 한다. 비교 대상은 **익명화된 집단 통계**여야지, 회사·관리자가 "당신의 점수"를 보는 것과는 다른 문제다. 온보딩 선언 문구를 "당신만 봅니다 + 비교는 항상 100% 익명 집단 기준입니다"로 확장한다.

### 보완 5. 벤치마크 모수 확보
동료 비교를 넣으려면 "동료군 평균"이 존재해야 하는데, 개인용 출시 초기엔 사용자가 소수라 통계적으로 의미 있는 평균을 만들 수 없다 — 전형적인 콜드스타트 문제.

→ **해결**: 기존 B2B 테넌트들의 실데이터(이미 확보된 협업 로그)를 **익명화·집계**해서 초기 벤치마크 모수로 사용한다. B2B는 세일즈가 안 됐을 뿐 데이터 자체는 살아있는 자산이다.
- 개인 식별 정보(이름, 소속 조직) 완전 제거, 지표값만 집계
- 표시 시 "B2B 테넌트 N개, M명 데이터 기반 초기 벤치마크"처럼 출처를 투명하게 명시 (사용자 신뢰 확보)
- 개인용 사용자가 충분히 쌓이면(예: 500명+) 벤치마크 모수를 개인용 데이터로 전환
- **최소 표시 기준**: 비교 모수가 10명 미만이면 표시하지 않고 "비교할 동료 데이터가 충분치 않습니다"로 대체 (1.2 실명 vs 익명 판단 기준 참고 — 니즈가 익명으로도 충족되는 항목이라 모수 부족 시 안 보여줘도 손실 없음)
- **법적 확인 필요**: B2B 계약 시 데이터 재활용(익명화 후 타 제품 벤치마크 활용) 조항이 있는지 확인 필요 — 없다면 약관 정비 또는 신규 동의 절차 선행 (PART 7 미결정 사항에 추가)

# PART 3. 제품 구조 (계승)

## 3.1 핵심 루프
```
OBSERVE (무엇이 바뀌었나) → UNDERSTAND (왜 중요한가)
  → ACT (이번 주 뭘 해볼까) → REFLECT (해봤더니) → OBSERVE
```
관계/업무/에너지/대화는 모듈이 아니라 이 루프를 뒷받침하는 **4개 데이터 관점(lens)**.

## 3.2 홈 화면

```
COLLABRAIN
Good morning, JooJoo.

YOUR TYPE                                   [ⓘ 8주 관찰 기반]
┌────────────────────────────────────┐
│         🛠  HARD WORKER              │
│  높은 업무량, 안정적 성과            │
│  (부하 상위 30% · 점수 상위 45%)     │
└────────────────────────────────────┘

YOUR SCORES                     나 · 4주 전 · 동료 평균(익명)
디지털화지수     78  ───▲6  ·  71
응답 적시성      62  ───▼9  ·  74     ← 가장 낮음
명확성           81  ───▲2  ·  75
적극성           69  ───▬0  ·  68
친절도           88  ───▲3  ·  80
경청·이해        73  ───▼4  ·  76

YOUR WEEK · August 3 – August 9
┌────────────────────────────────────┐
│ You're becoming more of a           │
│ coordinator this week.              │
│ Coordination  24% ──────→ 38%       │
│ Compared with your 4-week baseline  │
└────────────────────────────────────┘

WHY THIS MATTERS
Your communication outside normal hours
also increased this week — this lines up
with the drop in 응답 적시성 above.
[ View what changed ]
──────────────────────────────
THIS WEEK'S EXPERIMENT
응답 적시성가 4주 전보다 낮아졌어요.
Delegate one coordination task.
Define only the outcome + deadline.
[ I'll try this ]   [ Just observe this week ]
```

**설계 의도**: 서술형 카드 대신 **유형(Type) + 6축 점수(점수/추이/동료평균 병기)를 최상단**에 배치해 "한눈에 보이는" 요구를 충족한다. 서술형 카드("Why this matters", 실험 제안)는 그 아래에서 점수의 맥락을 설명하는 역할로 유지된다 — 점수만 있으면 성적표, 서술만 있으면 밋밋하다는 원칙(1.2)의 반영.

## 3.3 4개 관점
- **A 관계**: 인사이트 우선, 그래프는 증거. **점수/랭킹은 노출하되 대상은 항상 익명 집단** — 관계 강도의 "상대방 실명 비교"만 금지(사람 관계를 성적표로 만드는 것 방지). 상대방 개인 정보는 여전히 "관계의 내 쪽 절반"만.
- **B 업무**: 업무 유형 분해 + 자기인식 갭 + 동료 평균 대비 비율. **Phase 1은 3분류**.
- **C 에너지**: "번아웃" 네이밍 금지, "My Energy" 점수화. 사용자 맥락 override 가능("런칭 중이었어요") — 점수가 생겨도 이 override 기능은 더 중요해짐(맥락 없는 낮은 점수는 오해를 부르므로).
- **D 대화 습관**: 점수 + 패턴 서술 병기 + 관찰 지속 주수 + 동료 평균 대비. Phase 2 배치 유지(포지셔닝 리스크는 여전히 유효 — Phase 1엔 노출 안 함).
- **종합 유형(Work Type)**: B2B 히어로 맵 부활. 부하×점수 4분면("스마트 워커/히어로/하드 워커/협업 단절") → 개인 정체성 라벨. 상세는 1.6 참고.
- **횡단 실험**: 주 1개. **데이터로 관측 가능한 행동만 제안**. 실험 트랙(행동 변화 측정)과 관찰 트랙(baseline 재확인) 두 갈래 — 상세는 PART 2 보완 3. **가장 낮은 점수 축을 실험의 기본 트리거로 사용**(위 홈 화면 예시처럼). 실험 트랙은 셀프 약속 트래커와 같은 Commitment 엔진을 공유한다(PART 3.5.4).

# PART 3.5 설계담당 9개 기능 통합

설계담당이 CSV로 정리한 9개 기능(②~⑩, ①과 ⑪은 별도 범위로 제외)을 기존 4-lens 구조 위에 매핑한다. 완전히 새로운 프레임이 아니라, 지금까지의 구조(OBSERVE→UNDERSTAND→ACT→REFLECT 루프 + 4개 관점)를 채우는 구체적 기능들로 정리된다.

## 3.5.1 매핑 — 기존 구조와의 관계

| 설계담당 기능 | 기존 구조 매핑 | 비고 |
|---|---|---|
| ③ 주간 커뮤니케이션 거울 | **= 홈 화면(3.2)** | 명칭 통일. "미션 루프(수락→주중 인정→차주 회수)" 개념은 기존 "이번 주 실험" 루프와 동일 구조 — **"미션"이라는 용어가 더 직관적이면 실험→미션으로 명칭 교체 검토** |
| ② 아침 브리핑 | 신규 (횡단 기능으로 추가) | 매일 접점을 만드는 유일한 기능. 주 1~2회 사용 빈도라는 기존 전제를 daily로 끌어올리는 역할 — 리텐션 관점에서 가치 큼 |
| ④ 번아웃·과부하 조기 감지 | **= 관점 C(에너지)의 능동 알림 버전** | **명칭 충돌**: "번아웃"은 제품 표면에 안 쓰기로 한 단어. 내부 기능명은 이걸 써도 되지만, **사용자에게 보이는 문구는 계속 "work rhythm has changed" 류로 유지** |
| ⑤ 자동 회고·커리어 로그 | 신규 (횡단 기능으로 추가) | **범위 확정**: 관리자 제출용 아님. 본인만 보는 성과 아카이브 + 이직/자기평가 초안 생성 도구로 한정 (하단 3.5.3 참고) |
| ⑥ 동료 사용설명서 (Colleague Playbook) | **관점 A(관계)의 확장** | 익명 라벨이 아니라 실명 사용. 상세 원칙은 3.5.2 |
| ⑦ 관계 온도 레이더 | **= 관점 A(관계)의 마찰징후 감지 부분** | 이미 기존 계획에 포함됨. 월 2회 발동 상한 같은 구체적 운영 규칙은 신규 반영 |
| ⑧ 셀프 약속 트래커 | 신규, **실험 루프와 엔진 통합** | 상세는 3.5.4 |
| ⑨ 감사·인정 수지 코치 | 신규, **3차 타겟(리더 트랙) 온보딩 응답 기반 선택적 활성화** | PART 1.3 3차 타겟 참고 |
| ⑩ 재개 브리핑 | ⑥+⑦+⑧의 조회 표면 | 단독 기능이 아니므로 세 기능이 갖춰진 뒤에만 의미 있음 (설계담당 표와 동일 결론) |

## 3.5.2 동료 사용설명서(⑥) — 실명 사용 원칙

**결정: ⑥은 익명 라벨이 아니라 실명(또는 사용자가 아는 호칭)을 그대로 쓴다.** "상대 A와 일하는 법"은 아무 쓸모가 없다 — 이 기능의 존재 이유가 "누구와 일할 때 뭘 조심해야 하는지 기억하는 것"이라, 누구인지 알 수 없으면 기능 자체가 무의미해진다.

이건 기존 "관계의 내 쪽 절반만, 상대 실명 비노출" 원칙(3.3 A항목)과 표면적으로 충돌해 보이지만 실제로는 다른 문제다. 원칙을 구분하면:

| 원칙이 막으려는 것 | 적용 범위 | ⑥에 적용되는가 |
|---|---|---|
| 상대방을 **점수·평가·순위**로 노출 (사람 성적표화) | 관계 지도(A), 벤치마크 비교 | 여전히 금지 — ⑥에도 점수는 없음, 서술형 관찰만 |
| 상대방을 **실명으로 식별** | — | ⑥은 예외로 허용. 개인용 메모장 성격이라 식별이 기능의 전제 |

즉 **"이름을 아는 것"과 "점수를 매기는 것"은 다른 문제**였다는 게 이번 결정의 핵심이다. ⑥은 이름은 실명, 내용은 서술형 관찰(응답 패턴, 선호하는 형식 등)로 점수화하지 않는다.

**남는 리스크는 그대로 유지**: 동료 본인의 동의 없이 그 사람의 소통 패턴이 프로파일링된다는 사실 자체는 실명이든 익명이든 동일하다. 완화책도 유지: 이 프로필은 본인만 볼 수 있고, 내보내기·공유 기능 없음, 계정 삭제 시 함께 삭제.

**개발기획서(ClaudeCode용)에 미치는 영향**: 기존 데이터 모델은 `RawMessage.speakerLabel`을 전부 익명 라벨("상대 A")로 설계했는데, ⑥ 기능을 위해서는 최소한 이 테이블에 실명(또는 Slack display name)을 별도로 연결하는 필드가 필요하다. 다음 개발기획서 갱신 시 반영 필요.

## 3.5.3 자동 회고·커리어 로그(⑤) — 범위 확정

- **포함하는 것**: 완료 선언·감사 수신·스레드 종결 기여 등을 주간 자동 추출 → 역량 축으로 분류 → 본인이 원할 때 자기평가서 초안/이력서 문구로 변환해주는 **개인 소유 아카이브**
- **포함하지 않는 것**: 관리자·회사에 전송·공유하는 기능. 데이터가 회사 시스템(HR 툴 등)과 연동되는 것도 범위 밖
- 이렇게 범위를 명확히 하면, 원래 우려("평가받는 도구로의 회귀")와 충돌하지 않는다

## 3.5.4 실험 루프 × 셀프 약속 트래커(⑧) 엔진 통합

두 기능은 구조가 같다 — **"약속(커밋)을 포착 → 상태를 추적(대기/이행/미이행) → 특정 시점에 반응"**. 차이는 약속의 출처와 반응 타이밍뿐이다.

| | 실험 루프 (기존) | ⑧ 셀프 약속 트래커 |
|---|---|---|
| 약속의 출처 | 시스템이 제안, 사용자가 수락 | 사용자가 실제로 동료에게 한 말에서 자동 추출 |
| 반응 시점 | 주간 회고 (다음 주 데이터로 변화 측정) | 마감 임박 시 개입 (무통보 지연 방지) |
| 목적 | 성장 루프 (다르게 해보기) | 신뢰 보호 (약속한 건 지키기) |

**결정**: 하나의 **Commitment 엔진**(추출·상태추적·트리거 로직)을 공유하고, `source: 'system_experiment' | 'self_promise'` 필드로 구분한다. 화면과 알림 타이밍은 목적이 달라 분리 유지 — 실험은 홈 화면의 주간 카드로, 약속 트래커는 마감 임박 시 별도 알림으로 노출된다.

이 결정은 개발기획서(ClaudeCode용)의 데이터 모델에도 반영 필요 — 기존 `Entry.experiment` 필드를 별도 `Commitment` 테이블로 분리하는 방향.

## 3.5.5 차별화 논거 보강 (PART 1.5 보완)

설계담당의 "MCP(범용 AI+Slack) 대비 차별점" 컬럼이 기존 차별화 근거보다 훨씬 구체적이다. 핵심 논리를 채택한다:

> 범용 AI에 Slack을 연결해서 매번 질문하는 방식(세션형 MCP)으로는 이 제품을 복제할 수 없다. 이유는 **베이스라인이 축적형 데이터**이기 때문이다 — "지난 6주간 평소 대비 무엇이 달라졌는가"라는 질문 자체가, 그 축적이 없으면 성립하지 않는다. 게다가 본인이 인지하지 못하는 변화(번아웃 전조, 관계 냉각)는 애초에 "질문"으로 끌어낼 수 없고 **능동 감지**가 필수라, 사용자가 무언가를 물어봐야 작동하는 세션형 도구 구조로는 원천적으로 재현 불가능하다.

이건 제품 차별화일 뿐 아니라, **왜 서버·DB·스케줄러가 결국 필요한지**에 대한 가장 강력한 논거이기도 하다 (지금 붙여넣기 방식은 이 축적·능동감지 가치를 온전히 살리지 못하는 임시 버전이라는 뜻).

# PART 4. 플랫폼 전략 — 왜 네이티브 앱을 만들지 않는가

## 4.1 결론
**반응형 웹앱(단일) + Slack DM 알림.** 네이티브 앱은 Phase 3까지 만들지 않는다.

## 4.2 판단 근거

| 기준 | 앱 | 웹 | 판정 |
|---|---|---|---|
| 사용 빈도 | 주 1~2회 | 주 1~2회 | **웹** — 주 1회 앱은 홈 화면만 차지하다 삭제됨 |
| 진입 마찰 | 설치 + 로그인 | 링크 클릭 | **웹** — Slack 알림→링크가 가장 짧은 경로 |
| 핵심 화면 성격 | — | 그래프·시계열은 큰 화면 필요 | **웹** — 앱을 만들어도 결국 웹뷰가 됨 |
| 심리적 저항 | "업무 분석 앱을 폰에 설치" | 링크 열기 | **웹** — 이 제품 최대 리스크(감시 느낌)를 앱이 증폭 |
| 과금 수수료 | 앱스토어 15~30% | 없음 | **웹** |
| 개발·배포 비용 | 높음 (심사·양대 OS) | 낮음 | **웹** |

## 4.3 앱을 만들어야 하는 조건 (미래 트리거)
아래 중 하나가 성립하면 재검토한다.
- 푸시 알림이 **핵심 가치**가 될 때 — 예: 실시간 개입("지금 3시간째 조율만 하고 있어요")
- 사용 빈도가 **일 1회 이상**으로 올라갈 때
- 오프라인 접근이나 위젯이 필요해질 때

Phase 1~3 범위에서는 셋 다 해당되지 않는다.

## 4.4 채널 역할 분리
- **Web = 제품 경험 전체** (반응형)
- **Slack DM = 알림 전용.** Slack을 분석하는 서비스가 Slack 안에서 제품 경험까지 제공하면 "감시당하는 느낌"이 증폭됨. 한 줄 요약 + 딥링크로 제한:
  ```
  Your weekly reflection is ready.
  You spent more time coordinating this week.
  → View your week
  ```

## 4.5 데스크톱 / 모바일웹 기능 배치
| Desktop | Mobile Web |
|---|---|
| 관계 지도(그래프 인터랙션) | 이번 주 상태(홈) |
| 업무 구성 상세, 시계열 | AI 인사이트 한 줄 |
| 심화 분석 | 실험 / 회고 응답, 자기인식 체크인 |

# PART 5. 로드맵

단계 구분은 데이터 축적 요구량 기준(1차=MVP / 2차=L1 프로파일 4주+ 축적 / 3차=2차 파이프라인 재사용 / 4차=개인·관계 베이스라인 6주+ 축적)으로 정렬한다. **서버 도입 시점과도 자연스럽게 맞물린다** — 능동 감지·스케줄러가 필요한 기능들이 정확히 2차부터 몰려있다.

**1차 (MVP, 서버 없음·붙여넣기 기반 — 지금 진행 중인 스프린트)**
③ 주간 커뮤니케이션 거울(=홈 화면) + ② 아침 브리핑은 **조회형만**(미응답 목록, 능동발송은 서버 필요라 제외) + 관점 B(3분류) + 관점 C + 종합 유형 + 6축 점수
→ 익명 벤치마크는 이 단계에서 실질적으로 표시 불가(사용자 모수 없음) — "준비 중" 표기 유지

**2차 (서버 도입 이후, L1 프로파일 4주+ 축적)**
관점 D(점수 포함) + 자기인식 갭 + **⑥ 동료 사용설명서** + **⑧ 셀프 약속 트래커** + ②③의 능동 발송 고도화(스케줄러·알림 활용)

**3차 (2차 파이프라인 재사용)**
**⑤ 자동 회고·커리어 로그**(본인 전용 아카이브로 범위 확정) + **⑨ 감사·인정 수지 코치**(타겟 세그먼트 결정 후)

**4차 (개인·관계 베이스라인 6주+ 축적)**
관점 A(관계 지도, 익명 비교) + **④ 에너지 조기 감지**(번아웃 명칭은 내부용으로만) + **⑦ 관계 온도 레이더** + **⑩ 재개 브리핑**

> 참고: 서버 없는 현재 스프린트(1차)의 상세 구현 스펙은 별도 문서(개발기획서 ClaudeCode용)에 있음. 2차부터는 그 문서의 "추가 개발 항목"(서버+DB, Slack OAuth, 진짜 알림)이 정식 범위로 들어온다.

# PART 6. 리스크

1. **Slack 연동 권한 장벽 (최대 리스크)** — 개인이 회사 워크스페이스에 앱 설치하려면 관리자 승인 필요한 경우 다수. 개인용 제품인데 설치에 회사 허락이 필요한 구조적 모순. 우회안: read-only 최소 스코프, 본인 export 업로드 병행 검토. **Phase 1 착수 전 실검증 필요**
2. **"감시당하는 느낌"** — Slack DM 역할 축소, 전체 삭제권, 모듈별 opt-out, 온보딩 프라이버시 선언(보완 4, 익명비교 조건 추가)
3. **패턴 서술 정확도** — 관찰 주수 표기 + "아니에요"/"맥락이 있어요" 피드백 버튼 + 소급 분석으로 초기 표본 확보
4. **점수/비교 도입에 따른 성적표화 리스크** — 서열화 언어 금지 원칙(1.2 톤 원칙)과 "행동 제안 필수 동반" 규칙으로 방어하지만, 실제 사용자 반응은 Phase 1 이후 정성 검증 필요. MBTI적 재미와 성적표의 경계는 카피라이팅 디테일에서 갈리므로 문구 하나하나 리뷰 필요
5. ** B2B 데이터 재활용의 법적 리스크** — 벤치마크 모수로 B2B 테넌트 데이터를 쓰려면 계약·약관상 재활용 근거가 있는지 확인 필요 (PART 7 참고)
6. **동료 프로파일링 리스크** — ⑥ 동료 사용설명서는 **실명**을 써서 동료 본인의 동의 없이 그 사람의 소통 패턴을 프로파일링함(실명 사용 확정, 상세는 3.5.2). 본인만 보는 데이터·내보내기 불가로 완화하지만, 리스크 자체는 익명화보다 커졌음 — 법적 검토 항목에 추가 필요
